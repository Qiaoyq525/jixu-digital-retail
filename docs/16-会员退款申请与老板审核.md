# 会员退款申请与老板审核

这是你本次明确提出的门店规则：会员说明退款原因，老板决定，收银员只看处理结果。当前使用课程模拟支付，支持整单退款，不产生真实资金到账。

## 你现在怎样操作

1. 先重启 Java 应用，等待启动完成，再刷新浏览器。程序会通过 V5 为订单追加申请与审核字段，已有订单、库存和积分继续保留。
2. 会员登录，在“我的订单”找到自己已支付的数码订单，点击“申请退款”，填写原因并提交。订单显示“退款待审核”；此时还没有退款，库存与积分保持原样。
3. 老板登录，在左侧“退款审核”查看待处理申请。核对商品与退货情况后选择批准或拒绝；拒绝必须填写原因。
4. 批准后订单变为“已退款”，本单商品数量回到库存，本单赠送积分和累计消费被撤回。拒绝后仍是已支付订单，会员能看到原因，也能补充说明重新申请。
5. 原收银员在自己的经手订单中查看申请状态、原因及处理结果。页面没有审批或直接退款按钮，后台接口也不允许其审批。

## 可以用这个小表验收

用自己刚购买的一件鼠标等数码商品，记下起始值。不要把这里的预期直接填写成“测试通过”。

| 阶段 | 订单状态 | 退款申请状态 | 库存与会员权益 |
|---|---|---|---|
| 收银员确认购买后 | PAID | NONE | 按订单扣库存、加积分和消费 |
| 会员提交申请 | PAID | PENDING | 不变 |
| 老板拒绝并说明原因 | PAID | REJECTED | 不变 |
| 会员重新申请 | PAID | PENDING | 不变 |
| 老板批准 | REFUNDED | APPROVED | 按原单退库存、撤回积分和消费 |
| 再次批准或退款 | 不再变化 | 不再变化 | 拒绝重复操作 |

## 读代码时先理解这三步

`OrderController` 接收申请和审核请求，当前身份取自登录会话。`OrderService` 检查角色、订单归属和申请状态；`CommerceMapper` 执行参数化 SQL。

| 请求 | 谁能执行 | 作用 |
|---|---|---|
| `POST /api/orders/{id}/refund-request`，`{reason}` | 订单所属会员 | 保存最新申请和原因 |
| `POST /api/orders/{id}/refund-review`，`{approve, reason}` | 老板 | 批准或拒绝待审核申请 |
| 旧 `POST /api/orders/{id}/refund` | 所有角色均不能直接执行 | 阻止绕过申请流程 |

支付状态和申请状态分开保存：`PAID` 表示交易仍有效，`PENDING` 只表示有人提出售后申请。老板批准时，审核结果、库存、流水、积分、消费和订单状态必须一同提交或回滚。

V5 增加 `refund_status`、`refund_reason`、`refund_review_note`、`refund_requested_at` 和 `refund_reviewed_at`。旧已退款订单保留原状态，系统不会伪造当时没有发生的申请记录。订单保存当前最新一次申请；历史操作记入日志。

本轮范围是会员本人订单的整单售后，散客订单、部分退款、真实资金支付和退货物流不在此流程内。已识别的旧种子演示订单仍只读，不能退回当前数码商品库存。普通订单列表最多加载最近 500 条；老板的退款审核使用独立的 `GET /api/refunds` 查询全部申请，较早订单的待审申请不会被普通列表上限遗漏。课堂演示仍以小规模本地数据为范围。

本文件记录规则、操作与待验收项目；自动化或浏览器检查是否通过，以本轮实际验证记录为准，不能用此前 119 项测试代表新流程已验证。
