# 演示与答辩提纲

## 数码零售背景介绍

可以这样开场：本项目是极序数码零售管理系统，面向手机、电脑、智能手表和显卡等电子产品。老板乔胤淇统一管理商品、采购和经营数据，销售员负责收银，会员通过浏览器选购并排队结账。项目重点展示Java业务分层、优惠多态、事务库存与角色权限。

演示产品价格与参数用于课程样例，不用它们说明真实授权、市场报价或保修服务。当前按SKU管理库存，没有逐台设备序列号。

## 演示前准备

启动 MySQL 与 Java 应用，在浏览器确认首页可访问。用不同浏览器窗口或普通窗口加无痕窗口分别登录会员、销售员和老板，避免同一个会话反复切换造成混淆。

准备一份记录表：要买的商品、初始库存、会员初始积分和累计消费、销售员账号。演示之前先完整练习一次，不在正式展示时临时修改数据库。

演示账号见项目 README。当前运行展示使用桌面 java/版本3；旧版本仅作学习对照。正式演示创建一笔新的数码订单，此前“黄油可颂”旧演示交易已经按用户要求备份清理。其他旧种子订单若存在，保留只读保护，不用于正常退款。

## 建议演示顺序

| 顺序 | 操作 | 同时解释什么 |
|---|---|---|
| 1 | 老板登录，浏览总览与菜单 | 系统面向三个角色，权限在后端执行 |
| 2 | 搜索手机或显卡，编辑型号参数与上下架 | 页面 HTTP 请求如何进入 Controller，再经 Service 和 Mapper 写库 |
| 3 | 选择电子设备供应商，为显卡或电脑采购入库 | 一张采购单影响多张表，用事务保证一致性 |
| 4 | 会员登录、搜索商品、加入购物车 | 购物车属于当前会话用户，不能由前端随便指定别人 |
| 5 | 会员提交并查看柜台，再登录对应销售员确认 | 持久化票据、员工归属、手动确认与事务 |
| 6 | 查看成交订单与积分变化 | BigDecimal、优惠策略、订单快照与积分流水 |
| 7 | 销售员收银，切换另一个销售员 | 每个销售员只看到本人经手订单 |
| 8 | 老板查看库存流水、统计与导出 | 数据由真实订单聚合；CSV 输出需正确转义 |
| 9 | 会员申请退款，老板拒绝并说明原因；会员重新申请，老板批准 | 申请与拒绝不改库存积分；批准才回补库存、扣回积分，并发只能执行一次；收银员只读 |
| 10 | 老板打开收银员管理，新增账号并安排空闲柜台 | 管理员权限、四人上限、事务；有待办时不能调岗或停用 |
| 11 | 展示核心 Java 源码 | 沿一条真实请求讲清楚字段、参数、调用和事务 |

若展示时间较短，优先保留“会员提交 → 收银员确认 → 库存/积分 → 会员申请退款 → 老板审核 → 代码解释”的主线。采购和报表可以提前备好数据，减少重复录入。

## 一次数码设备交易的金额核对

新库默认满3000减100。以普通会员购买一台5499元的iPhone 16为例，在普通折扣1.00和默认优惠下，原价5499元、会员折扣0元、满减100元，实付5399元并赠5399积分。本单支付前仍是普通会员，支付后的累计消费达到银卡门槛，下一笔订单按银卡等级计算。实际演示前先确认后台优惠和会员已有消费，避免沿用此例假定值。

退款按订单记录的5399元和5399积分回退；不能用当下商品售价重新算旧订单。若查看到改版前订单的杂货名称，解释为保留的成交快照，勿改写为数码历史销量。

## 选哪些 Java 文件讲

不要按所有文件逐个念。选一条能串起业务的代码路径：

1. 订单请求对象：商品编号、数量、请求键分别是什么。
2. Controller：网址怎么对应 Java 方法，当前用户从哪里取得。
3. 业务服务：怎样检查商品和库存、计算优惠、创建订单。
4. Mapper：哪条 SQL 查询或锁定商品，参数怎样绑定。
5. 优惠接口与实现：同一个接口如何执行不同优惠算法。
6. 排队与员工管理：会员提交如何指定员工，人工确认如何付款，管理员新增收银员为什么要在后端检查四人上限。

推荐先在 IDEA 中固定打开 `ShopApplication`、`CatalogController`、`CatalogService`、`CatalogMapper`、`DiscountPolicy`、`OrderService`、`QueueService` 几个标签。可以使用“转到定义”“查找用法”展示调用关系，不需要把框架内部源码全部展开。逐段讲解见 `09-代码阅读与答辩详解.md`，具体 IDEA 操作见 `08-IDEA打开与运行.md`。

## 常见答辩问题

**为什么用 BigDecimal，而不是 double？**

因为商品金额按十进制精确到分，二进制浮点数可能出现小数表示误差。BigDecimal 配合明确的舍入规则，能够给出可解释的金额结果。创建金额时使用十进制字符串或数据库数值，不把有误差的 double 当成精确来源。

**为什么购物车有库存提示，结账还要检查一次？**

购物车展示之后其他顾客可能已经购买，提示只代表查询那一刻。结账时必须在事务中重新检查并锁定库存。

**两个顾客都看到库存是 1，怎样只卖出一件？**

两个请求可以同时到达，但对同一商品行的修改需要协调。事务通过行锁读取并核验库存，再执行带库存条件的更新。失败的一方收到库存不足，不产生部分订单。

**为什么不能只写 synchronized？**

它只能协调同一个 Java 进程中的线程，数据库可能有独立连接甚至其他程序访问。库存的最终一致性需要数据库约束和事务。本项目人工确认、员工安排和库存竞争由数据库锁与事务保护。

**线程池、阻塞队列分别做什么？**

线程池复用工作线程；阻塞队列是生产者与消费者交接任务的工具。当前业务票据由数据库保存并等待收银员点击确认，不自动交给后台线程付款。限量抢购实验已移除；如需讲解线程池，可打开实际并发测试，说明如何同时发请求并等待结果，不把测试功能讲成门店菜单功能。

**会员提交后为什么还需要销售员确认？**

提交只表达购买意向并生成等待票据，页面明确显示柜台和员工。服务端将确认接口限制为票据指定的销售员，核对后才一次性写订单、库存和积分。老板能看全店排队，不会冒充另一个员工完成这笔交易。

**为什么订单保存商品名称和价格，不只保存商品编号？**

因为商品以后可能改名、调价或下架。订单需要反映当时成交情况，因此明细保存快照。

**为什么密码不能让老板直接查看？**

密码只用于验证身份，不是经营数据。数据库存带随机盐的 BCrypt 哈希，登录时进行匹配；用户查询接口也不返回哈希。

**用户重复点击支付会怎样？**

前端先限制忙碌状态，后端再用 requestKey 和唯一约束识别同次请求。真正避免重复扣库存依赖后端幂等处理，不能只依靠按钮变灰。

**收银员为什么看得到申请却不能退款？**

这是门店自己决定的角色分工：会员表达退货意愿，老板核对后决定是否批准，原收银员保留业务知情权。权限在后端验证，隐藏按钮只是界面表现。申请时订单仍已支付，批准时才执行整单退款。

**退款为什么也是事务？**

退款同时涉及订单状态、库存、库存流水、会员消费和积分，必须一起成功或一起撤销。重复退款要被拒绝。

**用了哪些设计模式？**

优惠计算采用策略思路：不同规则实现统一接口。工厂如果只是按配置挑选或创建策略，准确称为简单工厂；只有存在不同创建者子类覆盖工厂方法的结构，才能称为工厂方法模式。按实际源码说明，不额外包装概念。

**AI 做了什么，你自己理解什么？**

可以如实说明 AI 协助生成代码、页面和文档，自己通过运行、追踪调用、修改输入、验证异常与并发结果逐步掌握。重点展示能够独立解释的核心 Java 路径、事务边界和失败处理。
