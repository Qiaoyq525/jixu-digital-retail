# 结合实际代码理解版本3

这份讲解从已经学过的普通 Java 出发。每看一个方法，先回答“谁调用它、参数是什么、做了什么、返回什么、失败怎么办”，再看框架注解。

文中的代码片段为了讲解省略了一部分细节。完整实现、实际校验与事务边界以 Java 源码为准；不能只看片段就修改结账逻辑。

## 先认识几个名字

| 名字 | 普通说法 | 本项目例子 |
|---|---|---|
| Controller | 接收浏览器请求的入口 | `CatalogController` |
| Service | 完成业务规则的对象 | `CatalogService`、`OrderService` |
| Mapper | 声明 SQL、读写数据库的接口 | `CatalogMapper`、`CommerceMapper` |
| Request | 保存本次请求输入的数据 | `ProductRequest`、`CheckoutRequest` |
| Response | 返回给浏览器的数据 | `ApiResponse<T>` |
| POJO | 普通 Java 对象 | `Product`、`SaleOrder`、`OrderItem` |
| Session | 服务端保存的一段登录会话 | 保存当前网站用户的身份 |
| Transaction | 一组一起提交或回滚的数据库操作 | 结账、采购、退款 |

这些英文名字主要描述职责。Service 里依然是 Java 字段、构造方法、方法调用、集合、条件判断和异常。

## 第一条阅读路线：商品查询

打开 `CatalogController`，找到 `products(...)`。它接收商品查询，调用 `service.list(...)`，把结果放进 `ApiResponse` 返回。

页面访问的地址可能是：

```text
GET /api/products?keyword=手机&categoryId=1
```

这行表示：用 GET 方法请求商品接口，查询关键字为“手机”，分类编号为 1。网页用 JavaScript 的 `fetch(...)` 发送请求，不会直接运行 SQL。

`@RequestMapping("/api")` 给控制器里的接口加上公共前缀，`@GetMapping("/products")` 指定当前方法的后半段路径，两者组成 `/api/products`。

`@RequestParam(required=false)` 表示查询参数可以不传。`Long categoryId` 使用包装类型，是为了允许 `null` 表示“没有选择某个分类”；`long` 不能保存 `null`。

接着按 `Ctrl+B` 跳到 `CatalogService.list(...)`。这个方法先取得当前用户，再根据角色决定是否只查询上架商品。这里体现一个关键规则：**前端控制显示，后端决定权限。** 即使会员手动拼出请求，也不能要求后端返回不该看到的商品。

最后打开 `CatalogMapper.list(...)`。它是一段带动态条件的 SQL：

```sql
SELECT p.*, c.name AS category_name
FROM product p
JOIN category c ON p.category_id = c.id
```

你已经会 MySQL，可以把这一步理解为平时写查询，只是 SQL 的输入值来自 Java 参数，结果映射成 `Product` 对象。

- `#{keyword}` 是参数绑定，MyBatis 通过 JDBC 把值交给数据库，不是把用户输入直接拼成 SQL 结构。
- `<if ...>` 根据参数决定是否增加某个查询条件，是 MyBatis 的动态 SQL 写法。
- 数据库字段 `category_name` 使用下划线；Java 字段 `categoryName` 使用驼峰命名。项目配置开启了相应映射。
- MySQL 返回多行，所以方法返回 `List<Product>`；每个列表元素对应一件商品。

这条链路可以概括成：

```text
浏览器 fetch
  → CatalogController.products
  → CatalogService.list
  → CatalogMapper.list
  → MySQL 查询
  → List<Product>
  → ApiResponse
  → JSON
  → 页面显示
```

返回给浏览器的 JSON 形式类似：

```json
{
  "success": true,
  "data": [
    { "id": 1, "name": "示例智能手机", "price": 3999.00, "stock": 20 }
  ],
  "message": "ok"
}
```

JSON 是传输用的文本格式；`Product` 是 Java 内存对象；`product` 表是数据库中的持久存储。三者可以描述同一件商品，却属于不同层次。

## Spring 帮忙创建对象，方法调用仍然是普通 Java

商品控制器中有这样的结构：

```java
private final CatalogService service;

public CatalogController(CatalogService service) {
    this.service = service;
}
```

可以逐句解释：

1. `private`：外部不能直接访问这个字段。
2. `final`：构造方法给字段赋值后，不能再让它指向另一个服务对象；这不代表服务对象的所有内部数据永远不变。
3. 构造方法的参数也叫 `service`。
4. `this.service` 是当前控制器的字段，右边的 `service` 是传进来的参数。
5. 后面调用 `service.list(...)`，就是普通的对象方法调用。

如果完全手动管理对象，你需要先创建服务，再把它传入控制器。Spring 的依赖注入负责安排这一步：它识别 `@Service` 等标记，创建并管理对象，再调用控制器构造方法传入依赖。

这里不应该给业务服务随意写 `new CatalogService(...)` 来替代框架管理，否则事务代理和其他依赖可能没有正确配置。

## Maven、JDBC、MyBatis、Spring Boot 各管什么

这几个名字经常一起出现，但解决的问题不同。

| 工具 | 本项目中的工作 | 与你熟悉的知识连接 |
|---|---|---|
| JDK | 编译和运行 Java | `javac`、`java`、标准类库 |
| Maven | 根据 `pom.xml` 下载依赖、编译、测试和打包 | 自动完成原本需要手工管理 jar 的工作 |
| JDBC | Java 操作关系数据库的标准接口 | 连接、执行 SQL、读取结果、事务 |
| MySQL Connector/J | 实现 JDBC 与 MySQL 的通信 | MySQL 的 Java 驱动 |
| MyBatis | 把 Mapper 方法与 SQL、结果映射关联 | 方法参数进入 SQL，查询行成为 Java 对象 |
| Spring | 管理对象及它们的依赖，提供事务等支持 | 构造方法传参、接口代理 |
| Spring Boot | 整理常用配置、启动内置 Web 服务器 | 从 `main` 方法启动整个应用 |

Maven 不保存商品数据，数据库不负责编译 Java，MyBatis 也不替你决定会员折扣规则。把职责分清，才能准确定位错误。

## 普通类、record、枚举和泛型

### 普通类保存业务对象

`Product` 用字段表示商品信息，用 getter/setter 提供访问方法。数据库查询和 JSON 序列化都可以借助这些访问方法读写数据。

不能因为写了 setter 就自动认为校验完整。本项目的创建、修改、采购、支付等业务规则主要放在 Service，输入约束也会在请求对象上声明。修改库存必须走相应业务方法，不能随意在任何地方调用 setter 就宣称库存已保存到数据库。

### record 用来携带请求或响应

例如：

```java
public record Item(Long productId, int quantity) { }
```

它声明一个有商品编号、购买数量的数据类型。Java 会生成构造方法、访问器、相等比较等。访问数量写 `item.quantity()`，普通 POJO 则常写 `item.getQuantity()`。

record 的字段引用不能重新赋值，但如果字段本身是一个可变集合，也不能据此认定集合内容绝对不可变。需要不可变快照时，代码还应使用复制等办法。

### 枚举约束一组固定值

`Role.ADMIN`、`Role.SALES`、`Role.MEMBER` 是固定角色，适合用枚举表示。它比把角色随手写成多个字符串更容易发现拼写错误。

`MemberLevel` 根据累计净消费得到等级和折扣率；本轮门槛为5000元银卡、15000元金卡、30000元黑金，普通会员在5000元以下。结账使用本单支付前的等级，本单消费影响后续等级。等级可以从消费推导，不必在每笔订单里手工写一套相同的 `if` 判断。

### 泛型说明容器装什么

- `List<Product>`：这个列表装商品。
- `Map<Long, Integer>`：键是商品编号，值是数量。
- `ApiResponse<List<Product>>`：统一响应中的 `data` 是商品列表。
- `ApiResponse<?>`：该位置没有进一步指定 `data` 的具体类型，并不等于可以跳过业务类型检查。

`ApiResponse` 中静态方法前面的 `<T>` 表示该方法自己的类型参数。调用 `ApiResponse.ok(products)` 时，编译器可以根据参数推导类型。

## 第二条阅读路线：优惠策略

这一部分适合先讲，因为它不依赖数据库也能计算。

### 接口说明统一能力

`DiscountPolicy` 定义：

```java
BigDecimal apply(BigDecimal amount);
String description();
```

意思是：“一种优惠策略要能接收金额，算出应用该优惠之后的金额，并提供说明。” 接口不负责规定每种优惠的具体算法。

### 抽象类保留共同步骤

`AbstractDiscountPolicy` 实现接口，并在 `apply(...)` 中调用子类的 `calculate(...)`，随后统一处理金额范围和小数位。`calculate(...)` 是抽象方法，由具体子类完成。

这同时体现：

- **继承**：`RateDiscountPolicy`、`FullReductionPolicy` 继承共同规则。
- **方法重写**：具体类重写 `calculate(...)`。
- **模板方法的思路**：父类固定主要处理步骤，子类补充不同算法。
- **封装**：折扣率等字段由对象内部保存，调用方只用统一方法。

### 多态发生在实际调用时

```java
DiscountPolicy policy = new RateDiscountPolicy(
        new BigDecimal("0.90"), "全场优惠");
BigDecimal result = policy.apply(new BigDecimal("4000.00"));
```

左边变量类型是接口，实际对象是比例折扣类。通过统一接口调用时，会运行实际对象对应的实现。换成满减策略，调用方式仍然相同，计算规则改变。

### 当前工厂是简单工厂

`DiscountPolicyFactory.create(...)` 集中创建全场折扣、会员折扣和满减策略，按执行顺序放进列表。它让收银计算器不用到处重复 `new` 各种策略。

**本项目没有不同工厂子类覆盖创建方法的层次，因此不能把它叫工厂方法模式。** `create` 是静态方法、方法名字里有 Factory，都不能单独证明它属于工厂方法模式。

策略解决“怎样计算”，工厂解决“创建哪些计算对象”。接口也不一定都构成策略模式，模式名称应结合实际用途解释。

### 按真实金额练一次

以一件原价4000.00元的数码设备为例，全场九折，金卡九五折，折后满3000减100：

| 阶段 | 计算 | 结果 |
|---|---|---|
| 全场折扣 | 4000.00 × 0.90 | 3600.00 |
| 会员折扣 | 3600.00 × 0.95 | 3420.00 |
| 满减 | 3420.00 − 100.00 | 3320.00 |
| 积分 | 实付金额向下取整 | 3320 分 |

金额用 `BigDecimal`，每个阶段明确保留两位小数。`HALF_UP` 表示常见的四舍五入，`DOWN` 用于正金额积分的向下取整。不要用 `==` 比较金额对象；金额大小通常用 `compareTo(...)` 比较。

## 第三条阅读路线：结账事务

打开 `OrderController.checkout(...)`，可以看到它把当前服务端登录身份和请求对象交给 `OrderService.checkoutFor(...)`。

前端提交的是商品编号、数量、可选会员编号和本次请求键。最终单价、优惠、积分和库存判断由后端从数据库取得，不能以网页计算或提交的金额为准。

### 为什么把身份单独传入

`auth.require()` 从 Spring Security 的当前请求上下文取出已经登录的用户。它不是相信前端发来的 `cashierId`。

员工可以为某个已有会员收银，所以请求中允许选择会员；这不意味着他能冒充其他销售员。会员自己的预览和排队则始终绑定本人。

### normalize 做输入整理，也确定锁顺序

`OrderService.normalize(...)` 检查商品列表和数量，合并重复商品，使用 `TreeMap<Long, Integer>` 按商品编号排序。

例如输入“商品 5 两件、商品 2 一件、商品 5 三件”，整理后得到“商品 2 一件、商品 5 五件”。这样每笔交易都按相同顺序处理商品。

`getOrDefault(id, 0)` 表示：这个商品此前没有数量时先按 0 计算；`put(...)` 保存合并结果。这里不是 Stream 的特殊功能，是普通集合操作。

### TransactionTemplate 明确事务范围

代码用 `TransactionTemplate.execute(...)` 包住真正的支付处理：

```java
return transactions.execute(status -> {
    // 查询并锁定、校验、保存订单、扣库存、更新会员等
    return order;
});
```

`status -> { ... }` 是 Lambda，可以理解为把“一次事务里需要执行的工作”交给事务工具。执行正常结束时提交；执行过程中抛出需要回滚的异常时回滚。

它和 `@Transactional` 都能组织数据库事务，但使用位置和调用机制不同。`@Transactional` 常通过 Spring 代理生效，同类内部直接调用自己的事务方法可能绕过代理。本项目订单服务使用显式事务工具，便于员工现场收银与会员人工确认复用同一套结账逻辑。

### 结账中要一起完成哪些修改

1. 锁定会员行，取得稳定的消费与积分数据。
2. 检查同一请求是否已有订单。
3. 按商品编号顺序锁定商品，检查上架和库存。
4. 计算当前实际应付金额。
5. 保存订单主表与商品明细。
6. 条件扣减库存，写库存流水。
7. 更新会员净消费与积分，写积分流水。
8. 如来自排队订单，按规则处理购物车和票据。
9. 记录业务日志，返回结果。

库存、订单、明细、流水和会员权益必须保持一致。如果第二种商品库存不足，前面做的数据库修改也应回滚。不是在 `catch` 里手动把每个字段“再改回去”，而是交给数据库事务撤销本事务未提交的变化。

### 行锁和条件更新分别保护什么

`SELECT ... FOR UPDATE` 在事务里锁定将要修改的记录。其他同时修改同一记录的事务需要等待；等待结束后，后来的事务按数据库锁规则读取并检查当前数据。

扣库存还使用类似条件：

```sql
UPDATE product
SET stock = stock - ?
WHERE id = ? AND stock >= ?
```

Java 检查影响行数。影响 1 行表示扣减成功；不满足条件则不能把交易视为成功。这是额外的数据库防线。

按商品编号固定锁顺序可以减少死锁机会，但不能据此保证任何数据库操作永远不会死锁。事务要尽量短，出现数据库异常仍需回滚和反馈。

### 幂等防止同次请求重复执行

`requestKey` 标记“这一次结账意图”，数据库设置唯一约束。同一次提交因重复点击或网络重试到达多次时，后端识别已有结果，避免再扣一遍库存。

请求键不能单独当作权限凭证。取出旧订单后还要确认会员、收银员归属；否则别人猜到或碰到同一个键就可能看到不属于自己的订单。新的一次真实购买则应使用新的请求键。

## 第四条阅读路线：退款为什么也要锁和事务

先看 `OrderService.requestRefund(...)`：验证当前用户是该订单的会员，只记录申请和原因。再看 `reviewRefund(...)`：仅老板能处理 PENDING 申请，拒绝必须有原因且不影响库存积分。批准才进入 `refundFor(...)`，再次验证老板和待审核状态，并在同一事务中恢复库存、扣回原积分、回退原消费额、更新订单及审核状态和流水。原收银员可以看申请与结果，不能审批或直接退款。

退款按**原订单快照**执行。商品今天已经涨价，不能据此给昨天的订单多退；会员今天换了等级，也不能重新计算当时获得的积分。

并发退款时，两次请求不能都把库存加回去。需要在数据库中协调订单状态变化，确保只能从有效已支付状态成功转换一次。只在页面把退款按钮隐藏不够。

当前积分没有兑换消费功能，退款撤回该订单赠送的积分。以后若加入积分抵现，需要重新定义积分不足、已兑换权益以及退款分摊规则，不能直接套用现在的假设。

## 第五条阅读路线：人工确认与收银员管理

先打开 `QueueController → QueueService → QueueMapper`，追踪“会员提交”和“收银员确认”两个不同请求。会员提交只保存等待票据；它不是支付请求。

### 会员提交保存了什么

服务端从当前登录会员的购物车读取商品编号和数量，生成快照。随后在可用柜台中按等待人数、柜台编号分配，保存 `cashier_id` 与 `counter_no`，返回 WAITING。`checkout_counter` 保存固定柜台与员工的对应关系，所以 1 号台不会因为另一员工停用而突然换人。

页面显示具体台号、员工姓名和账号。等待期间库存、订单和积分不变，票据在重启后保留。提交不预留库存或锁定价格，确认时仍需重新校验。

### 为什么确认接口要再次检查身份

收银员调用 `POST /api/queue/{id}/confirm` 时，服务端检查当前登录人是否为票据指定的启用 SALES。会员、老板和另一位销售员都不能代确认；这项限制必须放在 Java 服务里，不能只靠页面隐藏按钮。

在同一事务中，服务先协调柜台与票据，检查状态，再调用 `OrderService.checkoutQueued` 完成付款并写入 `order_id`。如果库存不足，整个事务回滚，票据继续等待，页面显示错误。已完成票据再次确认返回原订单，不能多扣一次库存。取消与确认同时到达时，也只能有一个结果生效。

### 管理员怎样新增和安排收银员

打开 `CashierController → CashierService → CashierMapper`。先找到管理员权限检查，再看用户名、密码和柜台校验，最后看数据库保存操作。创建请求不接收可信的角色参数，服务端直接设置 SALES；这解释了为什么会员不能伪造请求注册成收银员。

再思考：如果目前有 3 名收银员，两个创建请求同时到达，为什么不能各自“查到 3 人”后都插入？服务先在事务里锁定固定柜台，再检查人数并创建。后一个请求等前一个提交后重新检查，就会看到 4 人并被拒绝。

调岗前也要检查原柜台、目标柜台和员工的待办。如果还有等待票据，服务拒绝修改，让原员工先完成结账，或由会员取消提交。这样的规则让数据库中的负责员工与页面显示一致。

限量抢购实验已经移除。线程池与 `Future` 可在实际并发自动化测试中继续学习；会员业务票据本身仍在数据库等待人工确认。

## 异常如何回到页面

业务方法遇到库存不足、权限不足或非法状态，会抛出 `BusinessException`。它把异常情况从正常返回值中区分出来。

统一异常处理器负责把异常转换成适当 HTTP 状态和统一响应，例如：

```json
{
  "success": false,
  "data": null,
  "message": "商品库存不足"
}
```

前端的 API 封装读取失败消息，显示提示并恢复按钮状态。后端不应把 SQL、数据库密码或完整堆栈作为普通用户提示。

接口校验和业务校验都需要：请求约束可以拒绝负数量，业务方法还要确认对应商品确实存在、仍然上架、库存足够。

## 登录为什么不保存原始密码

注册时，`PasswordEncoder` 把密码计算成带随机盐的 BCrypt 哈希，保存到 `password_hash`。登录时用 `matches(...)` 比较提交的密码与已有哈希。

哈希是验证用的单向计算，不能用“解密出原密码”来描述。老板能看公开账号资料和经营数据，接口不会返回原密码或哈希。

登录成功后，服务端建立 Session，浏览器后续携带会话 Cookie。写操作还带 CSRF token，用来防止第三方站点借用已登录浏览器发起非本人预期的写请求。CSRF token、登录会话和角色权限各自解决不同的问题。

## Stream、集合与导出怎么讲

例如订单列表查询后的：

```java
orders.stream().map(this::loadItems).toList();
```

- `stream()`：把列表元素依次交给流水线处理。
- `map(...)`：把每张订单转换成补齐了明细的结果。
- `this::loadItems`：方法引用，可理解为 `order -> this.loadItems(order)`。
- `toList()`：收集成一个列表。这里不会因为用了 Stream 就自动并发执行。

有些统计适合 SQL 聚合，有些结果整理适合 Java 集合或 Stream。不要为了体现 Stream 把所有数据库记录都取到 Java 再统计。

CSV 导出把查询结果组织成文本，正确处理逗号、双引号、换行和潜在公式前缀，再使用 UTF-8 输出给浏览器下载。当前 CSV 实现中的字符串和字节处理，应按实际源码讲解；浏览器保存下载文件与 Java 显式调用 `Files.write(...)` 写服务器文件，是不同过程。

## 每讲完一段，自己做一次小验证

| 学到的内容 | 可以亲自做的操作 | 应能说出的原因 |
|---|---|---|
| 商品查询链路 | 搜索同一关键词、切换分类 | 参数怎样进入 SQL |
| 角色检查 | 会员与老板分别查看商品菜单 | 后端为何再次检查权限 |
| 优惠顺序 | 对照4000元数码设备示例计算 | 满减看的是哪个阶段金额 |
| 库存事务 | 尝试购买超过库存的数量 | 为什么不生成部分完成订单 |
| 幂等 | 查看测试中的重复请求用例 | 请求键与新购买有什么区别 |
| 退款 | 会员申请、老板拒绝或批准，逐步记录库存积分 | 为什么申请不退款、批准才执行，为什么按原单数据回退 |
