# Java 学习与代码讲解路线

目标是讲清楚每段 Java 代码的输入、处理和结果。无需先把 Spring 全部学完，再开始阅读项目。

## 第一遍：从已经熟悉的代码出发

先看商品、订单明细等普通类中的字段、构造方法、getter/setter，再看金额和数量校验。重点回答：

1. 这个类代表什么业务对象？
2. 字段保存什么信息，为什么选择这个类型？
3. 构造方法和普通方法有什么不同？
4. 方法接收什么参数，返回什么，什么时候抛异常？

`this.name = name` 中，左边是当前对象字段，右边是方法参数。`private` 限制外部直接修改数据；getter 提供读取入口。金额使用 `BigDecimal`，因为价格计算需要十进制精度。

`record` 是 Java 为“主要用于携带数据的类型”提供的简洁写法。比如一个请求对象只有商品编号和数量，record 会自动生成构造方法、访问器、相等比较等；访问器通常是 `quantity()`，不是 `getQuantity()`。它不等于数据库表，也不因为用了 record 就自动保存到数据库。

## 第二遍：追踪一次页面操作

以“浏览商品”为例：

```text
浏览器按钮或页面加载
    ↓ fetch('/api/products')
HTTP GET 请求
    ↓
Java Controller 接收请求
    ↓
Service 检查当前用户和查询条件
    ↓
Mapper 执行参数化 SQL
    ↓
MySQL 返回商品记录
    ↓
Java 转成响应对象，Spring 转成 JSON
    ↓
JavaScript 读取 JSON，把商品画到页面
```

HTTP 是浏览器与服务器通信的规则；JSON 是一种传递数据的文本格式。它们不会替代 Java 业务逻辑。浏览器与 Java 之间传的是请求和响应，不是直接调用数据库里的 Java 方法。

## 第三遍：理解常见注解

用户口中的“多加注解”往往指中文注释。Java 注释用于帮助人阅读，`@RestController` 这样的 Java 注解则能被框架读取，从而影响运行行为。

| 注解 | 在本项目中怎么解释 |
|---|---|
| `@SpringBootApplication` | 标记启动入口，开启 Spring Boot 的自动配置和组件扫描 |
| `@RestController` | 告诉 Spring，这个对象负责处理请求并返回数据 |
| `@RequestMapping` / `@GetMapping` / `@PostMapping` | 把网址和 HTTP 方法映射到 Java 方法 |
| `@RequestBody` | 把请求中的 JSON 转成 Java 请求对象 |
| `@PathVariable` | 读取网址中的编号，例如 `/orders/10` 的 10 |
| `@RequestParam` | 读取查询参数，例如 `?keyword=手机` |
| `@Service` | 把业务对象交给 Spring 创建和管理 |
| `@Mapper` | 告诉 MyBatis 为这个接口生成执行 SQL 的实现 |
| `@Select` / `@Insert` / `@Update` | 描述 Mapper 方法执行的 SQL |
| `@Transactional` | 让一组数据库修改成功时一起提交、失败时一起回滚 |
| `@Valid` 和约束注解 | 校验请求数据，例如非空、正数、长度范围 |
| `@RestControllerAdvice` / `@ExceptionHandler` | 统一把异常转换成客户端能理解的错误响应 |

注解需要逐个和所标记的方法一起解释，不要背成“框架魔法”。

## 依赖注入是什么

本项目的商品控制器 `CatalogController` 需要商品服务，它在构造方法参数中声明 `CatalogService`。Spring 启动时创建服务对象，再把它传给控制器。这个“由框架把对象传进来”的过程叫依赖注入。

构造方法注入与普通 Java 传参是相通的：控制器仍然在调用一个对象的方法。框架帮助安排对象的创建、共享与生命周期。

不要把“声明一个 `private final` 服务字段”理解成自动得到对象；真正建立依赖的是构造方法和 Spring 对象管理。

## Java 如何操作 MySQL

JDK 提供 JDBC 接口，MySQL Connector/J 实现与 MySQL 的通信，MyBatis 在 JDBC 上帮助我们执行 SQL 和映射结果。Maven 根据 `pom.xml` 下载这些依赖。

SQL 中的 `#{productId}` 表示参数绑定。它把 SQL 结构与输入值分开，不能用字符串拼接把用户输入直接放进 SQL。`${...}` 是文本替换，不能用于任意用户输入。

数据库表的一行、一个 Java 对象、一段 JSON 可能描述同一件商品，但属于三个不同层次：存储、内存、传输。Mapper 和框架在它们之间转换。

## 优惠策略和设计模式

优惠计算适合展示接口与多态：业务服务依赖统一的优惠接口，不必在结账方法中堆积所有优惠细节。普通折扣、会员折扣和满减实现各自计算规则，通过同一个接口调用。

如果有一个类根据优惠类型或配置选择并创建优惠对象，这通常称为**简单工厂**。它是常见的对象创建方式，但不是 GoF 23 种设计模式中的“工厂方法模式”。

源码的 `DiscountPolicyFactory.create(...)` 集中创建本次计算使用的策略列表，属于简单工厂。`DiscountPolicy` 是接口，`AbstractDiscountPolicy` 统一金额的非负与精度规则，`RateDiscountPolicy` 和 `FullReductionPolicy` 分别实现比例折扣、满减。普通优惠和会员折扣复用比例策略，只是折扣率和说明不同。

`AbstractDiscountPolicy.apply(...)` 先调用子类 `calculate(...)`，再统一规范金额，体现模板方法的思路：父类固定处理骨架，子类补充变化步骤。

**工厂方法模式**需要由父类声明创建产品的工厂方法，让不同的具体创建者子类决定生成哪一种产品。仅有一个 `switch` 返回不同实现，不能因此叫工厂方法模式。

答辩时应按源码实际实现命名，不要为了“凑模式”添加没有业务作用的层次。策略接口用于替换算法，工厂用于组织对象创建，二者解决的问题不同。

## 事务、幂等和并发

事务回答：“一次结账涉及多张表，如何避免只扣库存却没生成订单？”

幂等回答：“顾客连续点两次结账，如何避免扣两次？”项目通过请求键和数据库唯一约束识别同一次业务请求，还需要检查请求键属于谁，不能返回其他人的结果。

并发控制回答：“两个柜台同时读到库存为 1，如何保证最多卖一件？”检查和扣减必须在数据库事务中完成，使用行锁和条件更新；不能依赖页面禁用按钮，也不能仅用 Java 对象里的 `stock--`。

固定锁顺序回答：“两笔订单都买 A、B 商品，为什么不要一个先锁 A、另一个先锁 B？”按商品编号升序加锁，可以减少互相等待形成死锁的机会；会员消费也要协调，避免等级与积分丢失更新。

## 人工确认、员工安排与锁的分工

业务排队由 `QueueService` 保存数据库票据并等待指定销售员确认。`CashierService` 负责管理员创建收银员、四人上限、调岗和启停。先看“检查身份 → 检查条件 → 保存变化”的顺序，不必一次理解所有 SQL。

| 机制 | 在系统中的作用 | 你需要理解的例子 |
|---|---|---|
| 数据库行锁 | 协调同一柜台、库存或会员行上的事务 | 两个管理员同时新增第 4 名收银员，只能一个成功 |
| 事务 | 多个关联变化一起提交或回滚 | 账号创建成功却绑定柜台失败时，不能留下半成品 |
| 票据表与柜台表 | 保存等待状态和负责员工，支持重启恢复 | 有顾客等待时不能随意换掉负责收银员 |
| 幂等请求键与状态检查 | 同一次操作重试不重复成交 | 网络慢时重复确认，只生成一张订单 |

限量抢购实验已经从产品中移除。线程池、`CountDownLatch` 和 `Future` 仍可结合自动化并发测试学习；`BlockingQueue` 可以另做小练习。答辩时按当前代码说明，不把测试中的任务线程说成会员排队的自动付款流程。

## 建议阅读顺序

1. 普通数据类、枚举、业务异常。
2. 商品列表：Controller → Service → Mapper → SQL。
3. 登录与当前用户：Session、密码哈希、角色检查。
4. 订单预览与优惠策略：金额计算。
5. 真正结账：事务、库存、明细、积分。
6. 退款申请与审核：先区分会员申请、老板决定、收银员查看；再理解只有批准才执行状态判断和反向变更。
7. 排队、柜台与收银员管理：权限、人数上限和数据库一致性。
8. 统计和导出：Stream/聚合 SQL、CSV 转义、文件输出。

每次只选一个接口，写下“谁调用、参数是什么、改了什么、失败怎么办”。能独立用自己的话解释这一条链路，再阅读下一条。
