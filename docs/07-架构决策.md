# 架构决策记录

状态说明：“采用”表示本轮实现的工作选择，仍可根据实际运行和课堂要求修改。重要变更应同时更新代码、测试与文档。

## ADR-001：使用分层单体与同源静态前端

**状态：采用。**

背景：一个人完成课程项目，需要在 IDEA 中解释 Java 调用关系，部署与演示应尽量直接。

选择：一个 Spring Boot 应用提供页面和 API，按 Controller、Service、Mapper 分层；数据库使用一个 MySQL 实例。

考虑过的替代方案：前后端独立工程适合更复杂前端开发；微服务适合团队协作和独立扩容。两者都会增加启动进程、部署、网络错误和学习成本。

代价与边界：前端与后端同包发布，不能分别独立部署。本轮接受这个代价，用清楚的模块职责支持后续修改。

## ADR-002：Java 21、Spring Boot 3.5 与 MyBatis

**状态：采用，具体补丁版本由 pom 固定并验证。**

背景：电脑原先默认 JDK 8，但已下载 JDK 21；学生需要看懂普通 Java 类和显式 SQL。

选择：使用 Java 21，Spring Boot 3.5 系列与兼容的 MyBatis starter 3.0 系列。Java 21 允许用 record 表达简单请求响应，业务对象仍优先普通 Java 类和显式构造方法，不用 Lombok 隐藏方法。

替代方案：纯 JDBC 可帮助学习底层，但大量连接和结果映射代码会分散业务重点；JPA 可减少 CRUD，但会引入额外实体状态与隐式查询概念；更新的框架大版本需要重新核对兼容性。

代价与边界：MyBatis 需要手写 SQL，并承担字段映射和动态查询正确性；采用项目固定版本不代表可忽略依赖维护。课程展示使用的依赖组合需要编译与运行验证，未来公开部署前重新审查支持周期。

## ADR-003：MySQL、Flyway 和应用专用数据库账号

**状态：采用。**

背景：用户会 MySQL，业务存在多表事务、外键与并发库存要求。电脑已安装 MySQL 8.4.13。

选择：MySQL 保存业务数据，Flyway 管理表结构版本，初始化脚本创建项目数据库与专用账号；运行应用不使用 root。

替代方案：文件存储不足以直接表达关系与事务；H2 适合自动测试但不能完全替代 MySQL 锁验证；手动粘贴建表 SQL 容易造成不同电脑结构不一致。

代价与边界：需要额外的数据库服务和本地连接配置。迁移需要按版本追加，不能随意覆盖已执行脚本。数据库密码不能放进可分享源码。

## ADR-004：Session 登录、BCrypt 与 CSRF

**状态：采用。**

背景：系统通过同源浏览器页面使用，角色三种，暂不需要第三方移动客户端或分布式登录。

选择：Spring Security 管理 Session，会话 Cookie 标识当前用户；BCrypt 验证网站密码；写请求携带 CSRF token；服务端校验角色与数据归属。

替代方案：JWT 适合特定跨服务和客户端场景，但本项目还需要理解 token 保存、撤销和过期策略；自己用普通 Map 手写会话会重复实现成熟安全功能。

代价与边界：当前 Session 随应用实例管理，应用重启可能需要重新登录；多实例部署需额外共享会话方案。前端仍要正确处理 401、403 和 CSRF token 更新。

## ADR-005：数据库事务、固定锁顺序与幂等请求键

**状态：采用。**

背景：结账、采购、退款同时修改多张表，多位顾客会竞争相同库存，重复请求也可能同时到达。

选择：在独立业务事务内锁会员行，再按商品编号升序锁商品行，检查上架与库存；扣减库存用条件更新；订单、流水和会员变化同事务。唯一 requestKey 标记同次结账请求，并检查归属。

替代方案：只在前端防重复不足以保证服务端一致性；Java 进程锁无法约束其他连接；完全依赖失败后补偿会增加不一致窗口。

代价与边界：悲观锁会让竞争请求等待，事务要短，不应在锁内调用外部网络服务。固定锁顺序降低死锁风险，但仍需正确处理数据库异常，不能宣称系统永远不会死锁。

## ADR-006：持久化柜台分配与收银员人工确认

**状态：采用。**

背景：会员需要知道商品提交给了哪一个收银台，由该台的具体员工核对并确认。后台自动支付无法表达这项门店职责。

选择：V4 增加固定柜台与销售员绑定表；会员提交时保存商品数量快照和分配结果，选择可用柜台中等待人数较少的一台。票据保持 WAITING，只有指定启用 SALES 可以确认。认领、付款和票据完成同事务提交，正常等待单重启保留。老板查看全店，销售员只看自己的提交单。

替代方案：旧版内存队列加后台线程会自动结账，已被这次业务要求替代；按启用账号列表临时取模会让柜台与员工对应关系漂移；引入消息中间件也不能替代人工确认。

代价与边界：等待单不预留库存、不锁定价格，确认时重新校验；原员工有待办时拒绝停用或调岗，先完成或取消提交。缩减柜台只停止新分配，原启用员工仍能完成已有等待单。柜台绑定由初始化建立，管理员可在“收银员管理”调整至空闲柜台。当前不做排班日历或复杂交接流程。

## ADR-007：模拟支付与整单退款

**状态：采用。**

背景：展示重点是 Java 业务逻辑和一致性，无真实支付接入要求。

选择：模拟结账成功后形成 PAID 订单；整单退款恢复库存和本单积分、累计消费，防止重复退款。

替代方案：真实支付需要签名、异步回调、补单和对账；部分退货需要分摊优惠、记录已退数量和计算剩余可退款额。

代价与边界：不能把模拟支付当作真实资金系统，也不能声称存在真实退款到账。部分退款可作为后续版本需求，单独定义优惠分摊规则。

## ADR-008：先形成可演示版本，再依据实现完善材料

**状态：采用。**

背景：用户希望通过阅读完整代码逐步明确需求，老师允许 AI 协助，答辩强调 Java 代码可解释性。

选择：保留需求和模块约定，迭代实现与测试，随后用真实代码和运行结果校对架构、类图、测试记录与演示脚本。

代价与边界：初稿文档可能出现概念类名，必须标注并在代码稳定后校对；不得提前把计划中的测试写成通过。AI 协助应如实表述，不能用改文件名等方式代替理解代码。

## ADR-009：数码零售改版采用追加迁移

**状态：采用。**

背景：项目已经有本机数据库和实际操作数据，本轮将业务背景改成极序数码，需要替换旧演示商品，同时保留事务与库存演示的可追溯性。

选择：保留V1建表文件，新增V2数据迁移。旧种子SKU与名称同时匹配时，更新电子商品资料；不重置商品主键、库存、历史订单明细、积分、购物车或排队票据。全新库由Java初始化相同电子商品。用户自定义内容及已修改优惠按条件保留。

代价与边界：旧订单明细仍可能包含改版前商品名与单价，这代表当时成交事实；迁移不伪造电子商品历史销量。商品描述保存参数，但没有声称实现序列号追踪、保修或真实设备服务。


## ADR-010：改版前种子演示订单只读保留

**状态：退款保护仍采用；指定旧演示订单后续按用户要求备份清理，2026-11-02。**

后续情况：用户随后明确要求删除“黄油可颂”这一笔旧演示交易，已完成精确备份、清理及库存核对。以下保留当时选择与权衡，不能理解为该笔记录现在仍应出现在页面；通用旧种子订单退款保护继续有效。

背景：用户在订单中发现食品名称，查明为旧演示成交快照；旧商品编号已经被V2迁移为数码商品，退款会错误增加数码库存。

选择：按旧种子精确名称及缺失SKU快照识别，保留名称金额与状态，页面标记早期演示订单，服务端在写入前拒绝退款。

替代方案：改写旧订单会歪曲成交历史；删除订单会丢失记录；重建旧商品并迁移所有引用涉及库存、流水、订单等更大范围；独立干净演示库可用于后续展示，但本次保留现有数据。

代价与边界：这些已知旧种子订单不能办理整单退款，仍计入符合原统计规则的历史数据。本次没有修复V2复用商品身份的整个数据模型，也不适合把该迁移策略用于真实零售业务。正常数码订单的商品改名和调价不影响退款。新增自动化验证确保旧单拒绝后库存、积分、消费、流水、订单状态不变。

## ADR-011：管理员创建最多四名收银员，精简实验界面

**状态：采用，2026-11-02；由用户提出功能需求。**

背景：用户需要能安排额外收银员，但现有界面仅有两名预设员工；“限量抢购实验”与门店日常操作不符。

选择：增加管理员专属的收银员管理入口。公开注册仍创建会员，员工账号由管理员创建并固定为 SALES。最多四个收银员账号，含停用账号；创建时绑定空闲柜台，必要时开放该柜台。调岗和停用前检查待办，创建、调岗、启停均在事务中按固定顺序锁定柜台，以协调同时新增和会员提交。移除抢购实验页面、接口和专用运行时代码，保留实际订单的并发自动化测试及旧实验数据过滤。

替代方案：开放收银员自行注册会需要额外的身份审批；仅在前端限制四人可被接口绕过；有待办时强行换人会改变票据归属。当前采用管理员创建与明确拒绝条件，便于初学者理解和演示。

代价与边界：停用不释放账号名额，不支持员工删除、姓名修改、密码重置、批量换班或转移等待票据。历史订单继续引用原员工，避免把旧业绩迁给新人。后续若要替换离职员工，应另行定义账号与历史归属规则。


## ADR-012：会员申请退款，老板审核，收银员只读

**状态：按用户确认的业务规则实施；验证结果另见最新记录，2026-11-02。**

背景：原版会员没有申请入口，老板和收银员都能直接退款。用户要求申请由会员发起，决定权归老板，收银员只需要知情。

选择：V5在订单增加当前申请状态、原因、审核说明和时间字段。会员只能申请自己的有效已支付数码订单；老板处理待审核申请，拒绝要说明原因，会员可重提。只有批准会在事务中执行库存、订单、积分与消费的回退；原直接退款入口禁止执行。查询沿用既有订单范围，老板全部、会员本人、收银员本人经手。

替代方案：公开直接退款不符合当前门店规则；单独建设售后工单系统会引入更多表、退货物流和部分退款设计。当前以订单字段承载一次最新申请，操作日志记录动作，便于初学者理解。

代价与边界：当前没有部分退款、真实资金退款、退货物流或完整工单历史。被拒绝后重新申请会替换订单上的最新申请内容，历史动作以操作日志追溯。散客订单没有所属会员，不纳入会员自助申请。重复审批和并发冲突必须由后端条件更新及事务控制，不能仅靠按钮禁用。
